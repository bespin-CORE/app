# 일반 사용자 "내 정보·반려동물" 기능 설계

기준일: 2026-11-16. 상태: 사용자 승인 대기. 구현 전 문서이며 아래 내용은 아직 코드에 반영되지 않았다.

## 의도

회원가입한 일반 사용자가 기존 PetClinic의 보호자 정보(이름·주소·도시·전화번호)와 반려동물을 **본인 것에 한해** 직접 등록·수정한다. 전체 보호자 검색·명단과 타인의 반려동물·진료 기록은 직원(수의사, `STAFF`)만 본다.

현재는 `/owners/**` 전체가 직원 전용이고(`account/SecurityConfig.java:19`), 로그인 계정(`users`)과 보호자(`owners`) 사이에 연결이 없어 일반 사용자는 이 기능을 쓸 수 없다.

## 목표

| 기능 | 일반 사용자(본인 것만) | 직원 |
| --- | --- | --- |
| 보호자 정보 등록·수정 | 가능 | 전체 가능(기존 화면) |
| 반려동물 등록·수정 | 가능 | 전체 가능(기존 화면) |
| 진료 기록 조회 | 가능 | 전체 가능 |
| 진료 기록 추가 | 불가 | 가능 |
| 보호자 검색·전체 명단 | 불가 | 가능 |

## 하지 않는 것

- 예약과 등록 반려동물의 연결. 예약은 지금처럼 반려동물 이름을 직접 입력한다.
- 회원가입 폼 변경. 보호자 정보는 로그인 후 "내 정보"에서 처음 입력한다.
- 보호자·반려동물 삭제, 계정 탈퇴.
- 직원이 기존(계정 없는) 보호자를 계정에 연결해 주는 기능.
- Flyway 전환, 임시 서버 배포. 배포는 별도 지시가 있을 때 한다.

## 실패로 보는 경우

- 일반 사용자가 어떤 주소·폼 값 조작으로든 타인의 보호자·반려동물·진료 기록을 보거나 바꿀 수 있다.
- 직원용 `/owners/**` 화면의 기존 동작이나 기존 테스트가 깨진다.
- 임시 서버의 기존 MySQL 데이터가 손상되거나 수동 스키마 변경 없이는 앱이 뜨지 않는다.

## 제약

- 원본 패키지 `org.springframework.samples.petclinic`과 `owners`·`pets`·`visits` 구조를 유지한다(AGENTS.md).
- MySQL은 `spring.sql.init.mode=always`와 `CREATE TABLE IF NOT EXISTS`로 스키마를 만든다. 이미 있는 테이블에 컬럼을 추가하는 문장은 이 방식으로 자동 적용되지 않는다.
- 화면 문구는 모든 `messages*.properties`(11개)에 키를 동기화한다(`I18nPropertiesSyncTest`).
- 실제 검증 경로는 Maven이다. Gradle은 시도하고 결과를 보고한다.

## 접근 방법

1. **`/my/**` 전용 화면을 새로 만든다(선택됨).** 주소에 보호자 번호가 없고 서버가 로그인 계정으로 본인 보호자를 찾는다. `/owners/**`는 직원 전용 그대로다. 타인의 보호자를 지목할 수단이 없어 접근 통제 누락 위험이 가장 작다. 컨트롤러와 상세 화면을 새로 만드는 비용이 든다.
2. **기존 `/owners/{번호}`를 일반 사용자에게 열고 요청마다 소유 검사.** 코드는 적지만 경로 9개 중 하나라도 검사가 빠지면 타인 정보가 노출되고, 직원 화면에 역할별 분기가 생긴다. 사용자가 보안상 이유로 기각했다.
3. **보호자 필드를 `users`에 합친다.** 원본 구조 유지 지침과 맞지 않아 제외했다.

## 결정 사항

### 사용자가 정한 것

- 접근 방법 1.
- 일반 사용자는 진료 기록을 보기만 하고 추가는 직원만 한다.

### 설계자 판단(승인 시 함께 확인 필요)

- **연결은 `owners`에 컬럼을 추가하지 않고 새 테이블 `owner_accounts`로 한다.** 앞선 대화에서는 `owners.user_id` 컬럼을 말했으나 바꿨다. 이유: 새 테이블은 `CREATE TABLE IF NOT EXISTS`로 임시 서버에 자동 생성되어 수동 `ALTER`와 사람 인계가 필요 없다. 컬럼 추가는 MySQL 8.0에 `ADD COLUMN IF NOT EXISTS`가 없어 자동 적용이 안 된다.
  - 컬럼: `owner_id`(PK, `owners.id` FK), `user_id`(UNIQUE, `users.id` FK). 계정 하나에 보호자 하나, 보호자 하나에 계정 하나.
  - h2·mysql·postgres 세 `schema.sql`에 모두 추가한다.
  - JPA에서는 `Owner`에 선택적 일대일(`@OneToOne` + `@JoinTable`) 필드 `account`로 매핑한다.
- **전화번호 검증을 10자리에서 10~11자리 숫자로 넓힌다.** 현재 `Owner.telephone`은 `\d{10}`이라 한국 휴대전화 번호(예: 11자리)를 입력할 수 없다. 일반 사용자가 직접 입력하게 되면 바로 막히는 문제다. DB 컬럼은 `VARCHAR(20)`이라 스키마 변경은 없다. `telephone.invalid` 문구를 11개 파일에서 함께 고친다. 직원 화면의 검증에도 같이 적용된다.
- 직원 계정도 로그인 사용자이므로 "내 정보"를 쓸 수 있다.
- 로그인 후 이동 위치(`/reservations`)는 바꾸지 않는다.

## 동작

### 경로

| 경로 | 동작 |
| --- | --- |
| `GET /my/profile` | 본인 보호자 정보, 반려동물, 진료 기록을 보여 준다. 보호자 정보가 없으면 `/my/profile/edit`로 보낸다. |
| `GET·POST /my/profile/edit` | 보호자 정보가 없으면 새로 만들어 현재 계정에 연결하고, 있으면 수정한다. |
| `GET·POST /my/pets/new` | 본인 보호자에 반려동물을 추가한다. |
| `GET·POST /my/pets/{petId}/edit` | 본인 반려동물을 수정한다. |

- 보호자 정보가 없는 상태로 `/my/pets/**`에 오면 안내 문구와 함께 `/my/profile/edit`로 보낸다.
- `{petId}`는 **본인 보호자의 반려동물 목록 안에서만** 찾는다. 없으면 404다. 타인의 반려동물 번호와 존재하지 않는 번호를 구분하지 않는다.
- 진료 기록 추가 경로는 `/my/**`에 만들지 않는다. 기존 `/owners/{ownerId}/pets/{petId}/visits/new`는 직원 전용 그대로다.
- 반려동물 검증(이름 중복, 미래 생일, 종류 필수)은 기존 `PetController`·`PetValidator`와 같은 규칙을 쓴다.

### 접근 통제

- `SecurityConfig`: `/owners/**`, `/admin/**`는 `STAFF` 그대로. `/my/**`는 로그인 필수로 명시한다.
- 본인 보호자는 항상 서버에서 `Principal`의 사용자명으로 조회한다. 요청 값으로 보호자를 고르지 않는다.
- 폼 바인딩은 허용 목록으로 제한한다. 보호자 폼은 `firstName`, `lastName`, `address`, `city`, `telephone`만, 반려동물 폼은 `name`, `birthDate`, `type`만 받는다. `id`, `account`, `pets`는 요청으로 바꿀 수 없다.
- 기존 직원용 `OwnerController`·`PetController`·`VisitController`의 바인더에 `account*` 차단을 추가한다. 새 `account` 필드가 생기면서 폼 값으로 연결된 계정 정보를 건드릴 수 있게 되는 것을 막기 위한 최소 변경이다.
- 같은 계정이 동시에 보호자 정보를 두 번 만들려 하면 `user_id` UNIQUE 제약으로 한쪽이 실패하고, 실패한 요청은 `/my/profile`로 보낸다.

### 화면

- 상단 메뉴에 로그인 사용자 모두에게 "내 정보" 항목을 추가한다. "보호자 찾기"는 지금처럼 직원에게만 보인다.
- `/my/profile` 화면은 새 템플릿이다. 보호자 번호가 든 링크와 "진료 추가" 링크가 없다.
- 입력 폼은 기존 `owners/createOrUpdateOwnerForm.html`, `pets/createOrUpdatePetForm.html`을 재사용한다. 두 폼은 `action` 없이 현재 주소로 제출하므로 그대로 쓸 수 있다.

## 테스트로 고정할 것

- 일반 사용자: `/owners`, `/owners/find`, `/owners/{id}`, 진료 추가 경로가 모두 403.
- 비로그인: `/my/**`가 로그인 화면으로 이동.
- 보호자 정보 생성 시 현재 계정에 연결되고, 다시 들어가면 수정으로 동작.
- 사용자 A가 사용자 B의 반려동물 번호로 `/my/pets/{petId}/edit`를 GET·POST하면 404이고 B의 데이터가 바뀌지 않음.
- 폼에 `id`, `account.*` 값을 섞어 보내도 무시됨.
- 11자리 전화번호 허용, 9자리·12자리 거부.
- 직원용 기존 테스트(`OwnerControllerTests`, `PetControllerTests`, `VisitControllerTests`) 통과 유지.

## 구현자에게 맡기는 것

- 새 컨트롤러의 패키지·클래스 이름과 분할(`owner` 패키지 안을 권장).
- `/my/profile` 템플릿의 스타일(기존 `vc-legacy` 틀 또는 VetCore 새 스타일).
- 새 메시지 키 이름과 각 언어 번역.
- 기존 반려동물 검증 로직을 공유하는 방식.

## 검증과 미검증

- 실행할 검사: `cd app && ./mvnw test`. `./gradlew clean check`는 시도하고 결과를 보고한다.
- 구현 후에도 남는 미검증: 실제 MySQL에서 `owner_accounts` 자동 생성과 동작, 임시 서버 반영, 브라우저에서의 한글 화면·모바일 레이아웃.
- `docs/feature-spec.md`, `docs/db-design.md`는 구현 시 함께 갱신한다.
