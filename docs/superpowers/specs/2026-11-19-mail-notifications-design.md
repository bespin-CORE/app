# 메일 알림·이메일 인증·비밀번호 재설정 설계

기준일: 2026-11-19. 상태: 사용자 승인 대기. 구현 전 문서다. 담당: ③ 앱·WAS.

## 의도

예약한 사용자가 메일로 예약 상태를 확인하고, 비밀번호를 잊었을 때 스스로 되찾을 수 있게 한다. 메일은 팀 결정(Amazon SES) 대신 **새로 만든 프로젝트용 Gmail 계정의 SMTP**로 보낸다. Gmail은 AWS 밖 서비스라 GCP로 전환된 뒤에도 같은 코드로 발송된다. 팀 공유와 기술 선택 문서 수정은 사용자가 직접 한다.

## 목표

1. 예약 확정·변경·취소 즉시 확인 메일.
2. 치료일 전날 사전 알림 메일.
3. 신규 가입 시 이메일 필수. 기존 사용자는 로그인 후 팝업으로 이메일 등록을 유도.
4. 이메일 소유 확인(인증 링크). 인증된 주소로만 메일을 보낸다.
5. 비밀번호 분실 시 등록·인증된 이메일로 **재설정 링크**를 보내고, 링크에서 새 비밀번호를 정한다.
6. 이메일이 없거나 미인증인 사용자도 예약할 수 있다. 예약 직후 "예약 완료 + 이메일 등록·인증" 단계를 보여 준다.

## 하지 않는 것

- SES, 문자·카카오 알림톡, 수신 거부 설정, 마케팅 메일.
- 반송(bounce) 처리, 관리자용 발송 현황 화면.
- 이메일로 로그인(로그인 아이디는 그대로 사용자명).
- 임시 서버·EKS 배포와 시크릿 등록(별도 작업).

## 실패로 보는 경우

- 메일 발송 실패 때문에 예약·가입·비밀번호 변경이 실패하거나 느려진다.
- 같은 메일이 파드 수만큼 중복 발송된다.
- 재설정·인증 요청 응답으로 계정이나 이메일 존재 여부가 드러난다.
- 재설정 링크가 재사용되거나 만료 후에도 동작한다. 토큰 원문이 DB나 로그에 남는다.
- 부하 테스트 중 실제 메일이 대량 발송된다.
- 앱 비밀번호가 저장소나 로그에 남는다.

## 제약

- 원본 패키지 유지, 새 기능은 도메인 패키지로 추가(`AGENTS.md`). 새 패키지 `mail`과 기존 `account`를 쓴다.
- 신규 의존성 `spring-boot-starter-mail`(Maven·Gradle 양쪽). 팀 규칙상 승인 대상이며 이 설계 승인으로 갈음한다.
- 스키마는 아직 `schema.sql`(`CREATE TABLE IF NOT EXISTS`) 방식이다. 기존 테이블에 컬럼을 추가하지 않고 **새 테이블만** 만든다. Flyway 전환(#5) 때 그대로 옮긴다. h2·mysql·postgres 세 파일에 모두 반영한다.
- 화면 문구는 11개 `messages*.properties`에 키를 동기화한다(ko·en 번역, 나머지는 영어).
- 시각은 기존 `Clock` 빈(Asia/Seoul)을 쓴다.
- 앱 파드가 여러 개일 수 있고, DR 전환 시 DB가 GCP로 복제·승격된다.
- 이 기능은 PR #9(앱 반입, 미머지) 위에서 만든다. 새 이슈와 브랜치 `feat/<이슈번호>-mail-notifications`가 필요하다.

## 접근 방법

1. **발송 대기 테이블(outbox) + 주기 발송 작업 (선택됨).** 업무 트랜잭션 안에서 보낼 메일을 `mail_outbox`에 넣고, 몇 초마다 도는 작업이 집어서 보낸다. 실패하면 재시도한다. 예약이 저장되면 메일도 반드시 대기열에 있고, 조건부 UPDATE로 행을 집어 여러 파드에서도 한 번만 보낸다. 대기 행이 DB와 함께 GCP로 복제돼 전환 후 GCP 앱이 이어서 보낸다. 코드가 늘고 링크 메일이 몇 초 늦을 수 있다.
2. **그때그때 바로 발송.** 코드가 가장 적지만 Gmail 일시 오류나 파드 재시작 때 메일이 사라지고 재시도가 없다.
3. **메시지 큐(SQS 등).** AWS에 묶여 GCP 전환 때 함께 멈추고 인프라와 담당 조율이 늘어 제외했다.

사용자가 1을 골랐다. 이유: "장애가 나도 데이터가 이어진다"는 프로젝트 주제와 맞고 재시도로 일시 오류에 안전하다.

## 데이터

새 테이블 3개. 모두 `users.id`를 참조한다.

### `user_emails` — 계정 이메일 (사용자 1행)

| 컬럼 | 설명 |
| --- | --- |
| `user_id` | PK, FK → users |
| `pending_email` | 인증 대기 중인 주소. NULL 가능 |
| `verified_email` | 인증된 주소. **UNIQUE**, NULL 가능 |
| `verified_at` | 인증 시각 |
| `updated_at` | |

- 메일은 항상 `verified_email`로만 보낸다.
- 인증 전 주소는 중복을 허용하고, 인증 순간에 다른 계정의 `verified_email`과 겹치면 실패시킨다. 남의 주소를 먼저 등록해 진짜 주인의 가입을 막는 일을 피하기 위해서다.
- 이메일을 바꾸면 `pending_email`에 넣고 다시 인증한다. 인증 전까지 기존 `verified_email`로 계속 보낸다.

### `account_tokens` — 인증·재설정 토큰

| 컬럼 | 설명 |
| --- | --- |
| `id` | PK |
| `user_id` | FK |
| `purpose` | `VERIFY_EMAIL` 또는 `RESET_PASSWORD` |
| `token_hash` | 토큰의 SHA-256. **UNIQUE**. 원문은 저장하지 않는다 |
| `email` | 인증 대상 주소(`VERIFY_EMAIL`일 때) |
| `expires_at`, `used_at`, `created_at` | |

- 토큰은 32바이트 보안 난수를 URL-safe 문자열로 만든다.
- 유효 시간: 인증 24시간, 재설정 30분. 한 번 쓰면 `used_at`을 채우고(조건부 UPDATE) 다시 쓸 수 없다.
- 새 토큰을 발급하면 같은 사용자·같은 용도의 미사용 토큰은 무효화한다.

### `mail_outbox` — 발송 대기

| 컬럼 | 설명 |
| --- | --- |
| `id` | PK |
| `kind` | `RESERVATION_BOOKED`, `RESERVATION_CHANGED`, `RESERVATION_CANCELLED`, `RESERVATION_REMINDER`, `RESERVATION_SUMMARY`, `VERIFY_EMAIL`, `RESET_PASSWORD` |
| `recipient` | 받는 주소(넣을 때의 인증 주소, 링크 메일은 대상 주소) |
| `subject`, `body_text`, `body_html` | 넣을 때 완성한 내용 |
| `dedupe_key` | **UNIQUE**, NULL 가능. 사전 알림 중복 방지용 |
| `status` | `PENDING`, `SENDING`, `SENT`, `FAILED`, `SKIPPED` |
| `attempts`, `next_attempt_at`, `locked_until`, `last_error` | 재시도·잠금 |
| `created_at`, `sent_at` | |

- 내용은 넣을 때 완성해 둔다. 발송 작업은 사용자·예약을 다시 읽지 않는다.
- 링크 메일 본문에는 토큰 원문이 들어간다. 그래서 `SENT` 후 일정 기간(7일)이 지나면 본문을 지운다(구현자 재량: 정리 작업 또는 발송 직후 본문 비우기).
- `last_error`에는 예외 종류와 짧은 메시지만 남기고 앱 비밀번호·토큰은 넣지 않는다.

## 동작

### 발송 작업

- 몇 초(기본 5초)마다 실행. `PENDING`이면서 `next_attempt_at <= now`인 행, 또는 `SENDING`인데 `locked_until`이 지난 행을 조금씩(기본 20건) 고른다.
- 행마다 조건부 UPDATE로 `SENDING`과 `locked_until = now + 2분`을 걸어 집는다. 영향 행이 0이면 다른 파드가 가져간 것이므로 건너뛴다.
- 성공: `SENT`, `sent_at`. 실패: `attempts + 1`, `next_attempt_at`을 점점 늘려(예: 1분, 5분, 15분, 1시간) `PENDING`으로 되돌린다. 5번 실패하면 `FAILED`.
- 발송 직후 상태 저장 전에 파드가 죽으면 한 번 더 갈 수 있다(최소 1회 발송). 허용한다.
- `vetcore.mail.enabled=false`이면 집은 행을 보내지 않고 `SKIPPED`로 바꾼다. 나중에 켜도 쌓인 메일이 몰려 나가지 않는다. 부하 테스트 환경은 끈다.

### 예약 메일

- `ReservationService`의 예약·변경·취소가 성공하면 **같은 트랜잭션 안에서** 해당 사용자에게 인증된 이메일이 있을 때만 outbox에 한 행 넣는다. 없으면 넣지 않는다.
- 본문: 병원, 치료명, 치료일·시작 시각, 반려동물 이름, 예약 상태, 내 예약 링크.

### 사전 알림

- 15분마다 실행되는 작업이, 현재 시각이 "치료일 전날 18:00" 이후이고 치료 시작 전인 `BOOKED` 예약을 찾는다. 인증 이메일이 있는 사용자만 대상이다.
- `dedupe_key = REMINDER:{예약 id}:{치료일}`로 outbox에 넣는다. 이미 있으면(UNIQUE 위반) 무시한다. 파드가 여러 개거나 18:00에 앱이 꺼져 있었어도 한 번만, 늦게라도 보낸다. 치료일을 바꾸면 새 날짜로 다시 알린다.
- 전날 18:00 이후에 한 예약은 다음 주기에 바로 알림 대상이 된다(확인 메일과 함께 두 통이 갈 수 있다. 허용).

### 회원가입

- 가입 폼에 이메일 입력란(필수, 형식 검사, 최대 254자)을 추가한다.
- 가입 성공 시 `user_emails.pending_email`을 저장하고 인증 메일을 넣는다. 가입 완료 안내에 "인증 메일을 보냈습니다"를 붙인다.

### 이메일 등록·인증 화면 `/my/email`

- 로그인 필요. 현재 인증 주소, 인증 대기 주소, 입력·변경 폼, "인증 메일 다시 보내기"를 보여 준다.
- 다시 보내기는 같은 사용자 기준 1시간에 3번까지.
- `GET /verify-email?token=...`(로그인 불필요): 유효하면 `verified_email`로 옮기고 완료 화면. 다른 계정이 이미 인증한 주소면 "사용할 수 없는 주소" 안내. 만료·사용됨·없음은 같은 안내 화면.
- 인증에 성공했고 앞으로의 `BOOKED` 예약이 있으면, 예약 목록을 담은 `RESERVATION_SUMMARY` 메일을 한 통 넣는다. 인증 전에 한 예약의 확인 메일을 대신한다.

### 기존 사용자 팝업

- 로그인 사용자에게 인증 이메일이 없으면 공통 레이아웃에 팝업을 띄운다. "지금 등록"은 `/my/email`, "나중에"는 이번 로그인 세션 동안 숨긴다(세션 속성). 다음 로그인 때 다시 뜬다.
- `/my/email`과 인증 화면, 예약 직후 단계 화면에서는 띄우지 않는다.
- 직원 계정도 같은 규칙이다.

### 예약 직후 단계

- 예약 성공 후 인증 이메일이 없으면 `/reservations` 대신 `/my/email?after=booking`으로 보낸다. 화면 맨 위에 "예약이 완료되었습니다"를 보여 주고, 아래에 이메일 등록·인증 폼과 "나중에 하기"(→ `/reservations`)를 둔다.
- 인증 이메일이 있으면 지금처럼 `/reservations`로 간다.

### 비밀번호 재설정

- 로그인 화면에 "비밀번호를 잊으셨나요?" 링크 → `/password/forgot`(공개). 이메일을 입력받는다.
- 응답은 항상 같다: "등록된 주소라면 재설정 메일을 보냈습니다". 처리 시간 차이로 존재 여부가 드러나지 않게 실제 발송은 outbox로만 하고 요청 처리에서 하지 않는다.
- `verified_email`이 일치하는 사용자가 있고, 같은 사용자 기준 1시간에 3번 이하일 때만 토큰과 메일을 만든다.
- `GET /password/reset?token=...`: 유효하면 새 비밀번호 폼(가입과 같은 규칙 8~64자, 확인 입력). 무효면 같은 안내 화면.
- `POST /password/reset`: 토큰을 조건부 UPDATE로 사용 처리한 뒤 비밀번호를 BCrypt로 바꾼다. 같은 사용자의 남은 재설정 토큰을 무효화하고 **기존 로그인 세션을 모두 끊는다**(Spring Session JDBC의 사용자명 인덱스 조회). 완료 후 로그인 화면으로.
- 재설정·인증 경로는 CSRF를 유지한다(GET은 폼 표시만 하고 상태를 바꾸지 않는다). 단, 인증 링크 GET은 클릭만으로 끝나야 하므로 상태를 바꾼다. 토큰이 비밀이므로 허용한다.

### 링크 주소

- 메일 안 링크는 절대 주소다. `vetcore.mail.base-url`(예: 서비스 공개 도메인)로 만든다. AWS·GCP가 같은 도메인을 쓰므로 전환 후에도 같은 링크가 동작한다.

### 발송 설정

- Gmail SMTP: `smtp.gmail.com`, 587, STARTTLS, 인증. 사용자명·앱 비밀번호는 환경 변수(`MAIL_USERNAME`, `MAIL_PASSWORD`)로 주입하고 기본값을 두지 않는다. 운영에서는 Secrets Manager + ESO.
- 보내는 사람 이름: "VetCore". 주소는 발송 계정.
- 연결·읽기 타임아웃을 짧게(예: 10초) 둬 발송 작업이 오래 막히지 않게 한다.
- 메일 본문: Thymeleaf 템플릿으로 텍스트와 HTML을 함께 만든다. 한국어 기준, 사용자 언어 설정은 쓰지 않는다(발송 작업에 요청 맥락이 없음).

## 로그·개인정보

- 로그에 이메일은 마스킹(`ab***@domain`), 토큰은 남기지 않는다.
- 인증 링크·재설정 링크는 요청 로그에 쿼리 문자열이 남지 않도록 주의한다(nginx·ALB 로그는 인프라 담당에 안내).

## 테스트로 고정할 것

- 예약·변경·취소 시 인증 이메일이 있으면 outbox 1행, 없으면 0행. 메일 실패(발송기 예외)여도 예약은 성공.
- 발송 작업: 성공 시 `SENT`, 실패 시 재시도 간격과 5회 후 `FAILED`, 두 작업이 같은 행을 동시에 집지 못함, `enabled=false`면 `SKIPPED`.
- 사전 알림: 전날 18:00 이전에는 대상 아님, 이후 한 번만 생성, 두 번 실행해도 1행, 취소된 예약 제외, 미인증 사용자 제외.
- 가입: 이메일 필수·형식 검사, 가입 후 인증 메일 1행.
- 인증: 정상, 만료, 재사용, 다른 계정이 이미 인증한 주소, 인증 후 요약 메일.
- 재설정: 존재·비존재 주소의 응답 동일, 1시간 3회 제한, 30분 만료, 재사용 불가, 변경 후 기존 세션 무효, 토큰 원문이 DB에 없음.
- 팝업: 미인증 사용자에게 표시, "나중에" 후 같은 세션에서 미표시.
- 예약 직후 단계: 미인증이면 `/my/email?after=booking`, 인증 사용자는 `/reservations`.
- 테스트는 실제 SMTP 없이 발송기를 가짜로 바꿔 보낸 메일을 확인한다(새 테스트 의존성 없이).

## 구현자에게 맡기는 것

- 클래스·메서드 이름과 패키지 내부 분할.
- 메일 문구와 템플릿 디자인, 팝업 모양(기존 VetCore 스타일 안에서).
- 재시도 간격의 정확한 값, 정리 작업 주기.
- 발송 작업 스케줄링 구현(`@Scheduled` 등).

## 사람이 따로 할 일 (구현 범위 밖)

- 새 Gmail 계정 생성, 2단계 인증, 앱 비밀번호 발급(사용자).
- 팀 공유와 기술 선택 문서 수정(사용자).
- EKS 노드의 인터넷 출구(NAT)와 587 포트 허용 확인(① 네트워크).

- 실제 Gmail로 보낸 메일의 스팸 분류 여부.

## 개정 1 (2026-11-19, 팀 회의 결정 반영)

이 절이 위 내용과 충돌하면 이 절이 우선한다.

### 바뀐 결정
- **아이디 = 이메일.** 신규 가입은 아이디 자리에 이메일을 입력한다. 별도 이메일 입력란은 없앤다. 아이디(이메일)는 바꿀 수 없다.
- **아이디 규칙:** 앞뒤 공백 제거·소문자로 저장, 최대 25자. 형식: `이름부분@도메인`. 이름부분은 영문 소문자·숫자와 `.` `_` `-` `+`, 도메인은 영문 소문자·숫자·`-`로 된 이름들을 점으로 이은 것이며 마지막 이름은 영문 2자 이상. 이름부분은 점으로 시작·끝나지 않고 점이 연속되지 않는다. 특수문자는 필수가 아니다(`@`와 도메인의 점만 필수). 기존 `users.username`이 30자라 스키마 변경은 없다.
- **인증해야 로그인.** 신규 가입자는 인증 메일의 링크를 누르기 전에는 로그인할 수 없다. 로그인 화면에서 미인증 안내와 "인증 메일 다시 보내기"(이메일 입력, 1시간 3회, 응답은 계정 존재 여부와 무관하게 동일)를 제공한다.
- **기존 사용자는 그대로 둔다.** 이 변경 전에 만든 고객 계정(`user_emails` 행이 없는 계정)은 지금처럼 아이디로 로그인하고 메일 기능은 받지 않는다. 기존 아이디가 이메일 형식인 경우의 인증 경로는 현재 해당 계정이 없어 만들지 않는다.
- **직원 계정은 예외.** `STAFF` 계정은 인증 없이 로그인한다.

### 없애는 것
- 기존 사용자 이메일 등록 팝업(구 Task 7).
- 예약 직후 이메일 등록·인증 단계(`/my/email?after=booking`).
- 인증 후 "다가오는 예약 목록" 메일(`RESERVATION_SUMMARY`).
- `/my/email` 화면의 이메일 입력·변경 기능. 인증 대기·인증 주소 분리와 "다른 계정이 이미 인증한 주소(TAKEN)" 처리는 아이디 UNIQUE로 대신한다.

### 유지하는 것
- 발송 대기열, 예약 확정·변경·취소 메일, 사전 알림, 비밀번호 재설정 링크(인증된 아이디로 조회), 토큰·재시도·세션 종료 규칙.
- `user_emails` 테이블은 그대로 두고 인증 상태 기록에 쓴다: 가입 시 `pending_email = 아이디`, 인증 시 `verified_email = 아이디`. 스키마 변경 없음.

### 함께 고치는 점검 결과
1. 이메일 형식 검사를 위 규칙으로 강화(`x<other@a.com>` 같은 값 거부).
2. 회원가입 처리에서 동시에 같은 아이디로 가입할 때 500이 아니라 "이미 있는 아이디" 폼 오류가 되도록 트랜잭션 경계 정리.
3. 사전 알림 작업은 중복 키를 먼저 확인하고, 새로 넣을 때만 메일 본문을 만든다.
4. 컨트롤러의 클래스 전체 이름 사용을 import로 정리.
